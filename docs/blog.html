minRLM: A Token-Efficient
Recursive Language Model Implementation and Benchmark

The RLM paper showed that letting LLMs query their context through code unlocks capabilities not possible with a direct call. This post presents minRLM — a token-efficient implementation evaluated across 8 benchmark tasks — alongside an open framework for reproducing and extending these results.

Accuracy per task: minRLM (green) vs. vanilla LLM (blue) vs. official RLM (red). Three-runner comparison run, 20 queries per task, gpt-5-mini.
TL;DR
  • Three-way comparison: minRLM, vanilla LLM, and the official RLM implementation — 8 tasks, gpt-5-mini, 880 evaluations total.
  • In head-to-head comparison (20 queries/task): minRLM 70.0% · vanilla 61.9% · official 65.6% accuracy — using 8.8× fewer tokens than official and 3.2× fewer than vanilla.
  • In a dedicated 50-query run, minRLM reaches 76.8% accuracy across the 8-task benchmark suite.

  • Where it doesn't: pure-reasoning tasks with no data to retrieve (AIME: 88–90% vs vanilla 95%), and LLM-judge-scored open-ended tasks (GDP Val: 46% vs official 55%).
  • Includes an open benchmark framework (eval/) for running any RLM strategy against the same tasks.

Background: The RLM Paper

In December 2025, Recursive Language Models proposed storing input data as a variable in a Python REPL (a live code execution environment — think "run Python code and get the result back instantly") rather than pasting it into the context window. The model writes code to query the data; attention runs only on the results: search hits, filtered rows, extracted snippets.

This reframes the context window as a soft limit rather than a hard one. A 7M-character document becomes as accessible as a 7K one — navigated through code rather than read wholesale. The paper validated the approach on a small set of tasks using a reference implementation. This post extends that evaluation to a wider benchmark suite and describes a different inference loop design, optimized for token efficiency and production use.

┌──────────────────────────────────────────────────────────┐ │ Standard LLM │ │ │ │ [System prompt] │ │ [500,000 tokens of raw context] ← you pay for all of it │ [Question] │ │ → Answer (maybe right, maybe not) │ └──────────────────────────────────────────────────────────┘ ┌──────────────────────────────────────────────────────────┐ │ Recursive LLM (RLM) │ │ │ │ input_0 = "<500k chars stored in REPL>" ← never in prompt │ Task: "Count errors in last hour" │ ├──────────────────────────────────────────────────────────┤ │ LLM writes: │ │ │ │ errors = re.findall(r'\[ERROR\].*', input_0) │ │ cutoff = datetime.now() - timedelta(hours=1) │ │ FINAL(len([e for e in errors if parse_time(e) > cutoff])) │ │ │ → Code runs, answer returned. ~4k tokens total. │ └──────────────────────────────────────────────────────────┘

Implementation

minRLM is a production-ready RLM client designed with token efficiency and stability as primary objectives. The reference implementation uses a notebook-style loop: each iteration appends the generated code and a truncated REPL output to the conversation, so the context window grows across iterations (the raw data stays as a variable, but the accumulated code and outputs add up). Their own documentation notes the context "grows slowly" — the data confirms it: 47,767 average tokens per query vs minRLM's 5,428. Recent releases added history compaction to partially address this. The default sandbox is also a local exec call in the host process (Docker is supported but opt-in, and runs without a seccomp profile by default). My approach uses a single structured system prompt with typed task patterns and a Docker-sandboxed REPL with a custom seccomp profile. One structured call, flat token cost, fully isolated execution.

  • Single-shot prompt — one compact system prompt with typed patterns per task (structured data, MCQ, code retrieval, search & extract, math). The model picks the pattern and usually finishes in one or two iterations.
  • DockerREPL — every execution runs in a fresh container with a custom seccomp profile blocking all network and filesystem syscalls. No shared state, no sandbox escapes.
  • Sub-LLM delegation — for large MCQ and open-ended tasks, the agent pulls targeted evidence snippets and passes them to a focused sub_llm(task, evidence) call. The outer model never sees the raw data.
  • Reasoning-first — a chain-of-thought step before code generation. Helps on tasks that need planning (multi-hop retrieval, complex codebases). This is the default: from minrlm import RLM already gives you the reasoning variant.
from minrlm import RLM

client = RLM(model="gpt-5-mini")
answer = client.query(
    task="Which user had the most errors in the last 7 days?",
    context=open("huge_log_file.txt").read()  # can be 10MB+
)
# Data never enters the prompt. Token cost stays flat regardless of context size.

Why It Works

Attention is expensive and imprecise at scale. Given a 400K-character codebase in the prompt, the model must implicitly identify which ~2,000 characters are relevant to the question — and this retrieval often fails silently. With a REPL, the model explicitly specifies what to fetch; Python retrieves it deterministically; attention operates only on the result.

Three patterns account for most of the observed accuracy gains:

  • Search + sub_llm — the agent calls search(input_0, keyword) to pull snippets, then passes them to sub_llm(task, evidence). The outer model never touches the raw data.
  • Exact computation — regex counting beats LLM "reading" for structured data. No hallucinations, no substring traps like "incorrect".find("correct").
  • Code verification — for math, brute-force enumeration doesn't make sign errors or off-by-one mistakes. Algebraic reasoning does.

The Benchmark

The evaluation uses an open framework — eval/ in the repository — that runs any RLM strategy against 8 standardized tasks and records accuracy, token count, latency, and cost per query. Any runner implementing the interface can be added and compared under identical conditions.

Three runners were evaluated: minRLM, a vanilla LLM (direct call, no REPL), and the official implementation, all using gpt-5-mini. The comparison run used 20 queries per task per runner (480 total); a separate 50-query run was conducted for minRLM alone to reduce variance on the best-performing prompt.

Task 1 BrowseComp — Needle in a 7MB Haystack

Find one specific entity — a name, institution, place — inside a multi-document corpus up to 7MB. One correct answer, hidden somewhere in millions of characters. Vanilla can't even load the context. The query fails before it starts.

"Please tell me the name of the learning institution that fits the following criteria: A. In 2002, it held a three-day event from Thursday to Saturday… B. In 2003, it held its graduation ceremony on the fourth Sunday…"
Context: 7,726,462 characters

minRLM's code

# REASONING: Search the 7MB document for keywords from the criteria,
# gather snippets, and ask sub_llm to extract the institution name.
import re, json, datetime, collections

# Detect task type - no pipes, no MCQ → SEARCH & EXTRACT
has_mcq = any(f"{c})" in task_0 for c in "ABCD")
has_pipe = "||" in input_0[:10000]

head = input_0[:500]
tail = input_0[-1000:]
kws = re.findall(r'\b[a-z]{4,}\b', (head + tail + task_0).lower())
kws = list(dict.fromkeys(kws))[:20]

snippets = []
for kw in kws:
    for match, before, after in search(input_0, kw):
        snippets.append(before + match + after)
    if len(snippets) >= 10: break

combined = "\n---\n".join(snippets[:10])
answer = sub_llm(task_0, combined)
FINAL(answer)

Task 4 OOLONG — Structured Data Analytics

Pipe-delimited records (Field: Value || Field: Value), questions about frequency, counts, and comparisons. The classic trap: "incorrect" contains "correct". A vanilla LLM can stumble on this; re.findall(r'\bTrue\b', ...) can't.

"In the above data, is label 'False' more common, less common, or the same frequency as label 'True'? Give your final answer in the form 'Answer: False is [X] True'."
Context: ~6,260 characters of pipe-delimited records

minRLM's code

# REASONING: Count exact whole-word occurrences of "True" and "False" in input_0.
import re, json, datetime, collections

has_pipe = "||" in input_0[:10000]  # True - STRUCTURED DATA pattern

true_count  = len(re.findall(r'\bTrue\b',  input_0))

if   false_count > true_count: relation = "more common than"
elif false_count < true_count: relation = "less common than"
else:                          relation = "same frequency as"

FINAL(f"Answer: False is {relation} True")

Task 5 LongBench V2 — Long-Document MCQ

MCQ over long documents — novels, papers, technical manuals, reports. 50K–600K+ characters. Four statements, one true. The challenge is finding the relevant passage without reading the whole thing.

"In Agatha Christie's 'The Murder on the Links,' which statement is true?
A) Eloise Renauld did not grieve upon hearing of her husband's death because she no longer loved him.
B) The overcoat that Paul Renauld was wearing when he died did not fit him because he'd put on the vagrant's overcoat.
C) Bella Duveen killed Paul Renauld.
D) Madame Daubreuil overheard Paul Renauld's plan of feigning death, and took action."
Context: 329,526 characters (full novel)

minRLM's code (large MCQ path)

# REASONING: Use MCQ pattern - gather evidence snippets from the 330K char novel,
# then call sub_llm on curated evidence instead of the full text.
import re, json, datetime, collections

sz = len(input_0)   # 329,526 - triggers "large" path

# Extract terms from both question and answer options
opts = re.findall(r'[A-D]\)\s*(.+?)(?=\s*[A-D]\)|$)', task_0, re.DOTALL)
opt_terms = re.findall(r'\b[A-Z][a-z]{3,}\b|\b[a-z]{5,}\b', " ".join(opts))[:15]
q_terms   = re.findall(r'\b[A-Z][a-z]{3,}\b|\b[a-z]{5,}\b', task_0)[:10]
terms = list(dict.fromkeys(q_terms + opt_terms))[:25]

# Search for each term, deduplicate by page position
snips, seen = [], set()
for t in terms:
    for m,b,a in search(input_0, t)[:4]:
        pk = len(b)//2000
        if pk not in seen:
            snips.append(b[-2000:] + m + a[:2000]); seen.add(pk)

evidence = input_0[:3000] + "\n...\n" + "\n---\n".join(snips[:30])
answer = sub_llm(task_0, evidence[:50000])
answer = (answer or "A").strip().upper()
FINAL(answer)

Task 6 RepoQA — Code Retrieval from Large Codebases

Given a codebase dump and a natural-language description, return the exact function name and source. The model scans all signatures, picks the match, extracts the implementation. Up to 500K+ chars.

"Return the exact function that creates an error object specifically for operations that have been canceled, providing a standardized error handling mechanism. It accepts three optional parameters: a message string, an optional code, and an optional config."
Context: 732 chars (axios codebase index)

minRLM's code

# REASONING: Scan all function definitions, ask sub_llm to identify the right one,
# then extract and return its full source context.
import re, json, datetime, collections

is_code_task = any(k in task_0.lower() for k in ["codebase", "exact function", "code snippet"])

# Scan for all function definitions across Python, JS, TS, Java
all_funcs  = re.findall(r'^\s*def (\w+)\(', input_0, re.MULTILINE)
all_funcs += re.findall(r'\bfunction\s+(\w+)\s*\(', input_0)
all_funcs += re.findall(r'\b(\w+)\s*[=:]\s*(?:async\s+)?function\s*\(', input_0)
unique = list(dict.fromkeys(all_funcs))

# Build signature list for sub_llm to pick from
sigs = []
for nm in unique[:80]:
    sm = re.search(r'^\s*(def ' + re.escape(nm) + r'\([^)]*\).*?:)', input_0, re.MULTILINE)
    if sm: sigs.append(sm.group(1).strip())

func = sub_llm(f"{task_0}\nAll functions:\n{chr(10).join(sigs)}\nReply ONLY the function name.",
               input_0[:10000]).strip()
func = re.sub(r'[^a-zA-Z0-9_]', '', func)

r = search(input_0, "function " + func)
if r:
    m, b, a = r[0]
    FINAL(func + "||" + b[-800:] + m + a[:5000])

Task 8 GDP Val — Open-Ended Professional Tasks

Open-ended professional tasks — build a financial model, design a training program, draft legal analysis. No single correct answer. Scored by a judge LLM on output quality.

"You are a Quantitative Researcher at a proprietary trading firm expanding into single-name options. Develop a comprehensive American option pricing framework in a Python notebook. Implement and compare multiple methodologies (binomial trees, finite differences, Monte Carlo)."

minRLM's code (excerpt)

# REASONING: Implement CRR binomial tree, explicit finite differences,
# and Longstaff-Schwartz Monte Carlo in pure Python. Benchmark convergence.
import re, json, datetime, collections, math, random, time, statistics

def crr_binomial_american(S, K, r, q, sigma, T, N, option_type='put'):
    dt = T / N
    u  = math.exp(sigma * math.sqrt(dt))
    d  = 1 / u
    p  = (math.exp((r-q)*dt) - d) / (u - d)
    disc = math.exp(-r * dt)
    # Build price tree and work backwards with early exercise
    prices = [S * (u**j) * (d**(N-j)) for j in range(N+1)]
    values = [max(K - st, 0) if option_type=='put' else max(st - K, 0) for st in prices]
    for i in range(N-1, -1, -1):
        prices = [S * (u**j) * (d**(i-j)) for j in range(i+1)]
        cont   = [disc*(p*values[j+1] + (1-p)*values[j]) for j in range(i+1)]
        ex     = [max(K-st, 0) if option_type=='put' else max(st-K,0) for st in prices]
        values = [max(c, e) for c, e in zip(cont, ex)]
    return values[0]

Limitations & When Not to Use It

  • No data to retrieve — when there's nothing to search, the REPL is pure overhead. On AIME (pure math, no input), vanilla GPT-5-mini scores 95% vs minRLM's 88–90%. The enumeration still works — but you're paying extra for it. Use a plain call for pure reasoning tasks.
  • Short contexts (<8K tokens) — if everything fits in the prompt, a direct call is simpler and just as good. minRLM's advantage grows with context size; below ~8K it's a wash.
  • LLM-judge tasks (GDP Val) — judge LLMs reward verbose, well-formatted prose. minRLM writes terse, executable code. The code is often more useful, but it scores lower. GDP Val was the only task where official clearly outscored minRLM (55% vs 46%); vanilla scored 45%, essentially matching minRLM.
  • Stdlib-only sandbox — the Docker REPL runs Python 3.14 with no third-party packages. math, fractions, itertools, statistics, and collections are available. No numpy, pandas, or requests. Heavy numerical work needs pure-Python implementations and may take an extra iteration.

Conclusion

The results presented here suggest that the RLM inference pattern is most valuable in a specific and predictable regime: tasks where the relevant information is a small fraction of a large input. On BrowseComp (7MB corpora), CodeQA (400K-char codebases), and LongBench V2 (full novels), the code-based retrieval approach consistently outperforms both vanilla prompting and the reference implementation — at a fraction of the token cost. The gains are not marginal: in some cases vanilla LLMs cannot even attempt the task due to context overflow.

The token efficiency story is clear across all tasks. minRLM's single-pass structured prompt uses 8.8× fewer tokens than the reference implementation on average, and remains competitive or better on accuracy in 6 of 8 tasks. The two cases where vanilla outperforms minRLM — AIME (pure math, no retrieval benefit) and GDP Val (LLM-judge scoring that favors verbose prose) — are predictable from the task structure and not surprising.

A few things I would do differently with more time: larger sample sizes per task (20–50 queries introduces meaningful variance at these accuracy levels), multi-model evaluation beyond gpt-5-mini, and a more principled prompt search rather than manual iteration. The benchmark framework makes all of these straightforward to run — the infrastructure is there.

More broadly, the RLM technique seems underexplored relative to its practical value. Most production LLM calls that process documents, logs, or codebases would benefit from this pattern with minimal integration effort. The context window is rarely the right abstraction for data-heavy tasks; a REPL variable is.
