minRLM: A Token-Efficient
Recursive Language Model Implementation and Benchmark

Abstract

Recursive Language Models (RLMs) store large contexts in a Python REPL and let the model write code to query them — sidestepping context-window limitations without the orchestration overhead of general-purpose agents. minRLM is a token-efficient reimplementation of this idea, with a flat-cost inference loop, structured task routing, and reasoning-first code generation. Benchmarked against a vanilla LLM and the paper's reference implementation across 8 tasks (gpt-5-mini), it achieves higher accuracy while using 8× fewer tokens. The gains are largest on large-context retrieval, where vanilla fails entirely. On pure-reasoning and open-ended generation tasks it underperforms.

Background: The RLM Paper

In December 2025, Recursive Language Models proposed storing input data as a variable in a Python REPL rather than pasting it into the context window. The model writes code to query the data; attention runs only on the results: search hits, filtered rows, extracted snippets. A 7M-character document becomes as accessible as a 7K one — navigated through code rather than read wholesale.

The paper validated the approach on a small set of tasks. This post extends that evaluation to 8 tasks and describes a different inference loop design optimized for token efficiency.

┌──────────────────────────────────────────────────────────┐ │ Standard LLM │ │ │ │ [System prompt] │ │ [500,000 tokens of raw context] ← you pay for all of it │ [Question] │ │ → Answer (maybe right, maybe not) │ └──────────────────────────────────────────────────────────┘ ┌──────────────────────────────────────────────────────────┐ │ Recursive LLM (RLM) │ │ │ │ input_0 = "<500k chars stored in REPL>" ← never in prompt │ Task: "Count errors in last hour" │ ├──────────────────────────────────────────────────────────┤ │ LLM writes: │ │ │ │ errors = re.findall(r'\[ERROR\].*', input_0) │ │ cutoff = datetime.now() - timedelta(hours=1) │ │ FINAL(len([e for e in errors if parse_time(e) > cutoff])) │ │ │ → Code runs, answer returned. ~4k tokens total. │ └──────────────────────────────────────────────────────────┘

Implementation

The reference implementation uses a notebook-style loop: each iteration appends generated code and REPL output to the conversation, so the context window grows across iterations. The data confirms it: 41,781 average tokens per query vs minRLM's 5,198. minRLM takes a different approach:

  • Flat token cost — a single structured system prompt with typed patterns per task (structured data, MCQ, code retrieval, search & extract, math). The model picks the pattern and usually finishes in one or two iterations. Token cost stays constant regardless of iteration count.
  • Structured task routing — rather than open-ended exploration, the model detects the task type upfront and follows a proven minimal pattern, reducing reasoning overhead.
  • Reasoning-first — a chain-of-thought step before code generation. Helps on tasks that need planning (multi-hop retrieval, complex codebases). This is the default: from minrlm import RLM already gives you the reasoning variant.
  • DockerREPL — every execution runs in a fresh container with a custom seccomp profile blocking network and filesystem syscalls. The reference uses a local exec call by default.
  • Sub-LLM delegation — for large MCQ and open-ended tasks, the agent pulls targeted evidence snippets and passes them to a focused sub_llm(task, evidence) call. The outer model never sees the raw data.
from minrlm import RLM

client = RLM(model="gpt-5-mini")
answer = client.query(
    task="Which user had the most errors in the last 7 days?",
    context=open("huge_log_file.txt").read()  # can be 10MB+
)
# Data never enters the prompt. Token cost stays flat regardless of context size.

Why It Works

Attention is expensive and imprecise at scale. Given a 400K-character codebase, the model must implicitly find the ~2,000 relevant characters — and this retrieval often fails silently. With a REPL, the model explicitly specifies what to fetch; Python retrieves it deterministically; attention operates only on the result.

  • Search + sub_llm — search(input_0, keyword) pulls snippets; sub_llm(task, evidence) reasons over them. The outer model never touches the raw data.
  • Exact computation — regex counting beats LLM "reading" for structured data. No hallucinations, no substring traps like "incorrect".find("correct").
  • Code verification — for bounded, enumerable domains, code execution is exact. Less useful when the LLM can reason directly faster.

The Benchmark

The evaluation uses an open framework — eval/ in the repository — that runs any RLM strategy against 8 standardized tasks and records accuracy, token count, latency, and cost per query. Any runner implementing the interface can be added and compared under identical conditions.

Three runners were evaluated: minRLM, a vanilla LLM (direct call, no REPL), and the official implementation, all using gpt-5-mini. All three runners were evaluated together in a single 50-query run (1,200 evaluations total, 50 per task per runner).

Task 1 BrowseComp — Needle in a 7MB Haystack

Find one specific entity — a name, institution, place — inside a multi-document corpus up to 7MB. One correct answer, hidden somewhere in millions of characters. Vanilla can't even load the context. The query fails before it starts. ↗ Tevatron/browsecomp-plus

"Please tell me the name of the learning institution that fits the following criteria: A. In 2002, it held a three-day event from Thursday to Saturday… B. In 2003, it held its graduation ceremony on the fourth Sunday…"
Context: 7,726,462 characters

minRLM's code

# REASONING: Search the 7MB document for keywords from the criteria,
# gather snippets, and ask sub_llm to extract the institution name.
import re, json, datetime, collections

head = input_0[:500]
tail = input_0[-1000:]
kws = re.findall(r'\b[a-z]{4,}\b', (head + tail + task_0).lower())
kws = list(dict.fromkeys(kws))[:20]

snippets = []
for kw in kws:
    for match, before, after in search(input_0, kw):
        snippets.append(before + match + after)
    if len(snippets) >= 10: break

combined = "\n---\n".join(snippets[:10])
answer = sub_llm(task_0, combined)
FINAL(answer)

Task 3 RepoQA — Code Retrieval from Large Codebases

Given a codebase dump and a natural-language description, return the exact function name and source. The model scans all signatures, picks the match, extracts the implementation. Up to 500K+ chars. ↗ evalplus/repoqa_release

"Return the exact function that creates an error object specifically for operations that have been canceled, providing a standardized error handling mechanism. It accepts three optional parameters: a message string, an optional code, and an optional config."
Context: 732 chars (axios codebase index)

minRLM's code

# REASONING: Scan all function definitions, ask sub_llm to identify the right one,
# then extract and return its full source context.
import re, json, datetime, collections

is_code_task = any(k in task_0.lower() for k in ["codebase", "exact function", "code snippet"])

# Scan for all function definitions across Python, JS, TS, Java
all_funcs  = re.findall(r'^\s*def (\w+)\(', input_0, re.MULTILINE)
all_funcs += re.findall(r'\bfunction\s+(\w+)\s*\(', input_0)
all_funcs += re.findall(r'\b(\w+)\s*[=:]\s*(?:async\s+)?function\s*\(', input_0)
unique = list(dict.fromkeys(all_funcs))

# Build signature list for sub_llm to pick from
sigs = []
for nm in unique[:80]:
    sm = re.search(r'^\s*(def ' + re.escape(nm) + r'\([^)]*\).*?:)', input_0, re.MULTILINE)
    if sm: sigs.append(sm.group(1).strip())

func = sub_llm(f"{task_0}\nAll functions:\n{chr(10).join(sigs)}\nReply ONLY the function name.",
               input_0[:10000]).strip()
func = re.sub(r'[^a-zA-Z0-9_]', '', func)

r = search(input_0, "function " + func)
if r:
    m, b, a = r[0]
    FINAL(func + "||" + b[-800:] + m + a[:5000])

Long-document MCQ & structured data

Task 4 LongBench V2 — Long-Document MCQ

MCQ over long documents — novels, papers, technical manuals, reports. 50K–600K+ characters. Four statements, one true. The challenge is finding the relevant passage without reading the whole thing. ↗ zai-org/LongBench-v2

"In Agatha Christie's 'The Murder on the Links,' which statement is true?
A) Eloise Renauld did not grieve upon hearing of her husband's death because she no longer loved him.
B) The overcoat that Paul Renauld was wearing when he died did not fit him because he'd put on the vagrant's overcoat.
C) Bella Duveen killed Paul Renauld.
D) Madame Daubreuil overheard Paul Renauld's plan of feigning death, and took action."
Context: 329,526 characters (full novel)

minRLM's code (large MCQ path)

# REASONING: Use MCQ pattern - gather evidence snippets from the 330K char novel,
# then call sub_llm on curated evidence instead of the full text.
import re, json, datetime, collections

sz = len(input_0)   # 329,526 - triggers "large" path

# Extract terms from both question and answer options
opts = re.findall(r'[A-D]\)\s*(.+?)(?=\s*[A-D]\)|$)', task_0, re.DOTALL)
opt_terms = re.findall(r'\b[A-Z][a-z]{3,}\b|\b[a-z]{5,}\b', " ".join(opts))[:15]
q_terms   = re.findall(r'\b[A-Z][a-z]{3,}\b|\b[a-z]{5,}\b', task_0)[:10]
terms = list(dict.fromkeys(q_terms + opt_terms))[:25]

# Search for each term, deduplicate by page position
snips, seen = [], set()
for t in terms:
    for m,b,a in search(input_0, t)[:4]:
        pk = len(b)//2000
        if pk not in seen:
            snips.append(b[-2000:] + m + a[:2000]); seen.add(pk)

evidence = input_0[:3000] + "\n...\n" + "\n---\n".join(snips[:30])
answer = sub_llm(task_0, evidence[:50000])
answer = (answer or "A").strip().upper()
FINAL(answer)

Pipe-delimited records (Field: Value || Field: Value), questions about frequency, counts, and comparisons. The classic trap: "incorrect" contains "correct". A vanilla LLM can stumble on this; re.findall(r'\bTrue\b', ...) can't. ↗ oolongbench/oolong-synth

Task 8 GDP Val — Open-Ended Professional Tasks

Open-ended professional tasks — build a financial model, design a training program, draft legal analysis. No single correct answer. Evaluated by keyword matching against rubric criteria extracted from each task. ↗ openai/gdpval

"You are a Quantitative Researcher at a proprietary trading firm expanding into single-name options. Develop a comprehensive American option pricing framework in a Python notebook. Implement and compare multiple methodologies (binomial trees, finite differences, Monte Carlo)."

minRLM's code (excerpt)

# REASONING: Implement CRR binomial tree, explicit finite differences,
# and Longstaff-Schwartz Monte Carlo in pure Python. Benchmark convergence.
import re, json, datetime, collections, math, random, time, statistics

def crr_binomial_american(S, K, r, q, sigma, T, N, option_type='put'):
    dt = T / N
    u  = math.exp(sigma * math.sqrt(dt))
    d  = 1 / u
    p  = (math.exp((r-q)*dt) - d) / (u - d)
    disc = math.exp(-r * dt)
    # Build price tree and work backwards with early exercise
    prices = [S * (u**j) * (d**(N-j)) for j in range(N+1)]
    values = [max(K - st, 0) if option_type=='put' else max(st - K, 0) for st in prices]
    for i in range(N-1, -1, -1):
        prices = [S * (u**j) * (d**(i-j)) for j in range(i+1)]
        cont   = [disc*(p*values[j+1] + (1-p)*values[j]) for j in range(i+1)]
        ex     = [max(K-st, 0) if option_type=='put' else max(st-K,0) for st in prices]
        values = [max(c, e) for c, e in zip(cont, ex)]
    return values[0]

Limitations & When Not to Use It

  • No data to retrieve — when there's nothing to search, the REPL is pure overhead. On AIME (pure math, no input), vanilla GPT-5-mini scores 90% vs minRLM's 76%. The enumeration still works — but you're paying extra for it. Use a plain call for pure reasoning tasks.
  • Short contexts (<8K tokens) — if everything fits in the prompt, a direct call is simpler and just as good. minRLM's advantage grows with context size; below ~8K it's a wash.
  • Open-ended document generation (GDP Val) — these tasks ask for complete professional documents (reports, presentations, financial models). minRLM's REPL chain frequently returns short stubs or inability messages rather than the full document content, missing the rubric keywords the scorer checks for. On GDP Val: vanilla 56%, official 48%, minRLM 36%.
  • Stdlib-only sandbox — the Docker REPL runs Python 3.14 with no third-party packages. math, fractions, itertools, statistics, and collections are available. No numpy, pandas, or requests. Heavy numerical work needs pure-Python implementations and may take an extra iteration.

Conclusion

The RLM pattern is most valuable in a specific regime: tasks where the relevant information is a small fraction of a large input. On BrowseComp (7MB corpora) and CodeQA (400K-char codebases), minRLM outperforms both vanilla and the reference implementation at a fraction of the token cost. On BrowseComp, vanilla cannot even attempt the task; minRLM scores 94%.

The failures are equally informative. AIME (pure math), GDP Val (open-ended generation), and LongBench V2 (long-document MCQ) all underperform — predictably, given the task structure. The technique adds overhead when there is nothing to retrieve.

Future work: larger sample sizes (50 queries still introduces meaningful variance), multi-model evaluation beyond gpt-5-mini, and a more principled prompt search. The benchmark framework makes all of these straightforward to run.

More broadly, the RLM technique seems underexplored relative to its practical value. Most production LLM calls that process documents, logs, or codebases would benefit from this pattern. The context window is rarely the right abstraction for data-heavy tasks; a REPL variable is.
